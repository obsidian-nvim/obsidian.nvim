# Obsidian.nvim refactor investigation

Scope: `main` at `b5b6dae9` (3.16.10). This is a design investigation, not a proposal to rename every file or rewrite the plugin in one pass. The path-object removal branch was not identifiable among local refs, worktrees, or matching history; recommendations below apply to `main`, not to that diff.

## Recommendation in brief

Organize by **who owns a decision**, not by whether a function is pure, reads a line, or can be called over LSP. Keep the convenient scripting surface; make it an explicit facade over workflows. Put syntax behind a small, source-preserving Markdown query interface, with buffer access in a separate adapter. Use strings for paths, but keep the few path policies Neovim does not implement. Move workspace and editor policy out of `api.lua` as those seams become real. Do not make `Note`, `markdown`, or `workflows` the next junk drawer.

The first implementation should be **explicit LSP command dispatch**, not an `actions.lua` file split. The next high-leverage slice is **one source-aware Markdown reference query** shared by cursor lookup, search, and indexing. Both make the existing code easier to change without requiring a public rename.

## Evidence and limits

- 182 Lua modules under `lua/obsidian`, 677 unique literal internal `require` edges, including delayed imports. `api` is imported directly by 56 modules, `path` by 30, and `actions` by 16; nine internal modules import through `require('obsidian')`. 55 modules mention `Obsidian.`. The largest mutually reachable group contains 103 modules in this approximation. This is a measure of coupling, **not** 103 modules in a load-time cycle: it includes function-local and conditional imports and misses dynamic imports and global lookups.
- A fresh headless Neovim with runtimepath set, plugins disabled, and no `setup()` went from zero to **66 Obsidian modules** after `require('obsidian')`. This is a load-footprint measurement, not a startup performance claim. Bare require had not set `Obsidian` or registered any `obsidian.*` LSP commands; the latter happened at initialization. A separate initialization probe measured **4 advertised vs. 38 installed** command IDs, including `obsidian._toggle_checkbox`.
- `make test`: **1,195 cases, 92 groups, 0 failures, 0 notes** on the available Neovim 0.13 nightly. The declared floor is 0.11.0; CI tests 0.11.4, 0.12.0, and nightly. The probes below are not a substitute for those compatibility runs.

## 1. Workflows, scripting, and LSP are three different interfaces

**What exists.** `actions.lua` is simultaneously the scriptable workflow collection, an expression-keymap implementation, a set of picker controllers, and a collection of internal continuations for completion/hints. `api.lua`'s `__index` silently exports all of it. The Ex adapter (`commands/init.lua` and its subcommands) delegates only some workflows and still owns others. LSP `initialize.lua` installs every entry in `actions` into `vim.lsp.commands`; `workspace_execute_command.lua` looks up the table separately; `_code_action.lua` can register its own client command via `add { fn = ... }`. Completion emits `footnote_new`, `block_reference_new`, and `write_note`; link hints emit `link_suggestion`; hint acceptance talks to `vim.lsp.commands`. These are not all code actions, and not all scripting functions are meaningful with positional serialized arguments. A lazy `actions.__index` would also break enumeration if this dispatch is left unchanged.

**Target.** Keep `require('obsidian').actions` and the existing `require('obsidian.actions')` route for the deliberate scripting interface. Organize the implementations by feature (link navigation/editing, note creation, checkbox, properties, etc.). Add an owner-local private function first; extract a module when it hides meaningful behavior or is consumed through a second seam. Let the facade preserve useful old names; do not add another global action registry. Keep expression mappings returning keys in the editor adapter, with a compatibility forwarder for documented `api.smart_action`. A Lua workflow can be interactive and convenient without making prompting mandatory in the lower-level operation it calls.

Use an **explicit LSP command map** next to the LSP adapter: command ID → handler, with argument adaptation there. Code-action offerings reference command IDs; they own titles, kinds, applicability, and request-to-argument mapping. Completion and hints can reference a command without registering a menu action. Client-side dispatch and `workspace/executeCommand` fallback should share lookup and invocation for IDs deliberately supported by both. Decide explicitly which IDs are server-executable; derive advertised server IDs from that set rather than from the entire public Lua interface. Keep `register_command` (Ex extension) separate from `code_action.add/del` (documented LSP extension). Compatibility concerns: custom `fn` currently lives in the client command table; `del` only removes the menu entry; registration and initialization can overwrite the same ID. Define collision/ownership and cleanup semantics before changing them, and test existing third-party registration. Keep built-in `data` callbacks server-side; do not increasingly rely on function-valued metadata leaking into returned LSP objects just because the server is in-process.

A first PR can leave workflow bodies untouched: inventory ID producers, preserve the named behaviors and extension registration, explicitly reject unlisted IDs, then remove enumeration and implicit fallback. Test built-in and custom code actions, client and server fallback, hint acceptance, all completion continuations, stale block completion, repeated initialization, and invoking from a non-current buffer. Use protocol behavior rather than the current structure of `_code_action.actions` as the main assertion.

**Next slice: link navigation.** `actions.follow_link` calls `_definition.follow_link`, converts LSP locations to quickfix entries, then opens or picks. `_definition` calls `actions.new`/`new_from_template`, prompts, opens external URIs, and can modify text; `link.resolve_link_path` separately does a synchronous lookup for `includeexpr`. Move resolution policy to `link/resolve.lua` (name illustrative). Have it return candidates with a string path and `Range`, or distinguish missing/internal/external/attachment results as needed. No picker, prompt, editor opening, or LSP objects in the resolution contract. The interactive workflow handles creation/disambiguation/confirmation; definition converts results, and `includeexpr` keeps its synchronous, noninteractive flavor. Characterize current definition side effects before deciding whether to change them as a user-facing behavior; do not silently stop offering note creation on definition in a mechanical refactor. Cover exact source-relative matches, fallback order, anchors/blocks, external/autolink policy, and cancellation/no-match completion. Apply the same pattern to `actions.workspace_symbol`, which currently uses an LSP result (including `data.note`) as the picker data model.

## 2. Markdown: one namespace, not one parser

`parse/document.lua` is an exclusion-region scanner, not a full document parser. It already has a valuable seam: source lines in, ranges/context out, no buffer or Tree-sitter dependency. `document.lua` is the changedtick-keyed buffer snapshot adapter; `section.lua` builds headings, sections, and block candidates (including setext/table context). `parse/header.lua` only knows an ATX line and anchor rules. `header.lua` and `block.lua` provide editor lookup and rename workflows. `tag.lua` mixes normalization, source-aware extraction across YAML and inline text, and vault-wide edits. `parse/refs.lua` reads complete source references; `link/parser.lua` splits a **destination**, which is a different operation. These distinctions are worth naming.

Suggested destination as code is touched (not an atomic move):

```text
markdown/
  document.lua     source snapshot and contextual queries
  regions.lua      exclusion scanner, if separated from the document implementation
  buffer.lua       get(bufnr), revision/invalidation; returns the same snapshot shape
  sections.lua     structural query implementation (sections, headings, block candidates)
  references.lua  link/ref recognition; includes wiki/Markdown/autolink/footnote syntax
  tags.lua         inline recognition and source-aware tag occurrences, including YAML ranges
  list.lua         list marker + optional task; one representation
link/
  target.lua       split/join destination + anchor/block; not a source parser
  resolve.lua      choose candidate targets in a source/workspace context
```

Keep tag/heading/block **edits** outside `markdown/`; keep YAML a separate format module. Use `heading` for the Markdown concept in new names; leave `header` fields or aliases where changing them would break callers. `tag/parser.lua` is a reasonable alternative only if tag is the real owner of that interface and the parser stays independent of tag search and rename. Using `markdown/` wins here because links/tags/blocks share document inclusion policy and snapshots; a broad `parse/` groups by mechanism. Avoid `markdown/line/{types,tasks,list_items}` as a one-for-one translation. A small helper like `parse_atx` can be private beside structural queries unless a genuine lexical consumer needs it. Keep small widely shared syntax rules in the module that owns them rather than inlining repeated patterns. `parse/line/tasks.lua` largely projects a `ListItem` into another one-element result; collapse it internally to an optional task on a list item and keep a compatibility/test adapter only if needed. Likewise, `extract` returning an array and `parse` indexing `[1]` is not a useful convention for syntax that has at most one result.

**First slice:** keep the existing scanner and paths initially. Add one internal document-aware reference query, e.g. `references.on_row(snapshot, row)` with an optional `at(snapshot, pos)` only if it saves repeated caller policy. Migrate cursor lookup, cache extraction, and search to that query. Today they separately combine `lexical = true`, an origin range, `INLINE_EXCLUSIONS`, and whole-range comment checks. Keep neutral recognition separate from consumer-specific filtering: the cache can choose to record only wiki/Markdown and search can deduplicate, without either reimplementing Markdown eligibility. Give isolated-text tokenization an explicit name when necessary instead of a `lexical` switch with a different default policy. Audit tags/tasks next: YAML tags are not arbitrary `#text` inside frontmatter; checkbox extent must follow the parsed marker, not assume a fixed byte length for all Unicode task states. Do not remove legitimate distinctions between preview/UI, completion-on-incomplete-syntax, and normal document queries.

Use `Pos`/`Range` for internal zero-based bytes and half-open ranges per `CONTRIBUTING.md`; convert LSP, cursor, quickfix, and ripgrep fields at their adapters. `api.cursor_link`'s four returns (including an older mixed-convention tuple), `search.find_links`' scalar offsets, and `actions.BlockReferenceOpts`' LSP ranges show why simply moving files will not fix composability. Keep one record at the new seam; adapt legacy tuples as needed. Keep snapshots read-only by contract; reuse the buffer snapshot on the hot path, do not parse the same document per row, and do not eagerly collect everything for every request. Tests: frontmatter links and YAML tag ranges, multiline comments and fenced/indented code, HTML and code spans, setext and table cases, escaped wiki-table pipes, UTF-8, and changedtick invalidation. Compare buffer, file/index, and cursor behavior on common fixtures while allowing explicitly different projections. No AST or Tree-sitter migration required.

## 3. Remove `Path` representation, preserve filesystem and vault semantics

The object adds coercion (`string | Path`), operator overloads, derived fields, and a reverse edge from filesystem primitives into `api` for OS and workspace policy. Much of the interface is already `vim.fs`/`vim.uv` under another spelling. Replace the common operations outright with core functions available on the supported floor. Do not clone the class as twenty string wrappers.

There are distinct decisions to name and preserve:

| Concern | Owner and migration rule |
| --- | --- |
| Lexical join/parent/basename and ordinary stat | Core `vim.fs` / `vim.uv`, no wrapper merely for spelling. Distinguish normalization, absolute expansion, and realpath. |
| Canonical file identity, including new paths | Narrow file/path helper if needed. Existing `Path.resolve()` resolves the nearest existing ancestor in non-strict mode. In a temp probe, `vault/alias/new.md` normalized to itself, but `Path.resolve()` returned `other/new.md` because `alias` was a symlink. Preserve required strict/lenient and symlink semantics at workspace keys and URI/attachment confinement checks. |
| Descendant-relative path vs. general relative link | `vim.fs.relpath` (where supported and equivalent) for a descendant; keep a small explicit sibling-relative helper where links need `..`. Probed `vim.fs.relpath('/var/vault','/var/other/new.md')` → `nil`; plugin helper → `../other/new.md`. Specify cross-volume behavior before swapping implementations. |
| Workspace-relative display and path ownership | Workspace/link policy, not a filesystem method. `Path:vault_relative_path` currently selects a workspace, passes through already-relative input, and has a strict failure mode. `Workspace.find` (first configured `ws.path`, existing target) and `api.find_workspace` (most specific `ws.root`, lenient target) are not interchangeable. Name the two intents and test precedence before unifying any implementation. |
| Filename IDs, suffixes, writes and directories | Keep intentional behavior: append vs. replace extension, dotted IDs, template and destination rules, missing-path errors, binary writes, and existing directory permissions (the current `Path.mkdir` default is `0700`). Do not pull an unrestricted write/copy rewrite into a path migration. |

`fs.lua` already earns its keep through traversal, batching, ignore semantics, and sorting; `util/fs.lua` owns different operations (relative paths and atomic write). Put the remaining helpers under a clear owner and don't have low-level traversal infer workspace policy from `Obsidian.dir` when its caller already has the context. Also reconcile note-extension policy *intentionally*: `filetypes.lua` has a set, `api.path_is_note` duplicates it, and `fs.dir`/ripgrep use their own filters. Separate 'is a supported note filename' from 'should this query scan it'; test policy before deduplicating.

Run the branch against path characterization tests before deciding which compatibility is necessary: nested workspaces and `/vault` vs. `/vault-other`, macOS realpath aliases, symlinked ancestors of nonexistent files (including confinement), relative display paths, root/trailing separators, Windows drive/UNC paths where supported, filenames with spaces or multiple dots, `..` links, and directory permissions. Public migration is more than removing `require('obsidian').Path`: `Note.path`, workspace fields, `Obsidian.dir/buf_dir`, `note_path_func`/`note_id_func` arguments, and generated Vim help expose the object today. Prefer string-first internals, a narrow legacy conversion at documented interfaces while 3.x needs it, and one explicit 4.0 change for public path types. If the existing branch already breaks the public types, make that branch the planned major-release change rather than keeping dual types throughout core.

## 4. Replace `api.lua` by ownership, not by purity

| Existing responsibilities | Real owner |
| --- | --- |
| `_workspace_opts`, `find_workspace`, `resolve_workspace_dir`, note membership | Workspace lookup and effective options. Filetype predicate is separate from workspace admission and template/ignore policy. |
| `cursor_*`, `current_note`, visual selection | Editor adapters for an explicit buffer/window and source positions. Have `current_note` compose note loading with workspace lookup; move Markdown recognition behind the snapshot seam. Avoid ambient cursor fallback when a different buffer/position was supplied. |
| `open_buffer`, blink, opening strategies, input/confirm | Thin editor and prompt operations. Inline trivial wrappers if they encode no policy; centralize the ones that preserve opening/selection behavior. `open_note` composes link/note information with these adapters. |
| `format_link`, template folder, missing-note creation and reference rewriting | Link formatting, templates, and note/link workflows respectively. Keep format policy separate from rendering (and do not require mutable active state for an explicit source path). |
| Plugin discovery/docs path, OS/icons, attachment forwards, `dir`, actions metatable | Give discovery its runtime owner, use existing icons/attachment/fs owners, keep explicit compatibility forwards for documented callers. `util.lua` should be the remaining genuinely generic helpers, not another public route for policies. `util/text_insertion` belongs with note content edits; `util/rename` is already a multi-file refactor module in all but name. |

Child-process testing is a **test placement** choice, not a reason these functions must live together. Use in-process tests for source parsing, formatting, and planner logic. Temp directories work for path operations and note I/O. Use child Neovim where live buffers, windows, autocmds, LSP, or prompt/cancellation behavior matter, using the existing `tests/helpers.lua` wait helpers. Don't introduce generic ports for Neovim or the local filesystem just to mock them.

`builtin.lua` is lower priority. Own note IDs with note creation, link rendering with links, image rendering with attachments, and frontmatter projection with frontmatter when those modules are edited. Keep documented `builtin.title_id` working (and other supported callback names) as an explicit convenience or compat facade. Putting all implementations into `config/default.lua` would make defaults depend on feature loaders. Keep defaults declarative where possible and feature-leaf callbacks cheap/lazy. `util.urlencode` and date aliases should not pull whole domains into generic utility loading. In particular, `uri.lua` combines generic URL scheme/encoding (imported even by `link/parser.lua`) with the `obsidian://` parser and state-changing dispatch. Split generic URI helpers from the Obsidian protocol adapter before treating the namespace as a primitive. Keep `obsidian.uri` compatibility if needed. Preserve percent-encoded query delimiters and mutating-URI confirmation/confinement.

## 5. State and feature lifecycle are the next structural issue

`Workspace.set` currently selects a workspace, mutates global state, creates directories, resets caches, sets up UI, starts or pauses sync, and fires callbacks/events. `autocmds.lua` registers at require time, also selects workspaces on buffer entry, and owns keymaps, LSP, embeds, footer, hints and write hooks. `client.lua` is a compatibility view onto the same state, not an independent instance. This is why moving the other large files wholesale would leave the coupling in place.

- Keep one owner of workspace transitions. Separate read-only context selection from actual activation; reading/previewing/link resolution should not switch the workspace unless explicitly intended. For async workflows, capture source path/buffer, the relevant workspace/effective options, and where needed a revision or generation at the start. Don't pass a universal context bag or replace `_G.Obsidian` with a different singleton that every leaf imports. Keep the documented global usable for scripts while avoiding new inward dependencies on it.
- Example of a context leak: `search.find_notes` documents `opts.dir` but its sync wrapper forwards only `search` and `notes`; `resolve_note_async` accepts an explicit directory but probes subdirectories from active options. Add a two-workspace fixture with different root/options and a focus switch during an async result before extracting those responsibilities. Distinguish bugs found during extraction from deliberate behavior changes.
- Give setup and attach/detach explicit, idempotent functions where lifecycle matters; make imports side-effect-light. Cover disabled config, repeated setup/attach, workspace changes, and stale async updates with child tests. Preserve existing custom callbacks and User autocmd contracts (including spelling) until a migration is documented.
- Put first-party optional features under `obsidian.plugins` or retain the existing `core-plugins` name as a migration alias; pick one spelling. `slides` should own its viewer, slide-specific parser, and optional presentation contribution. Audio recorder is a second concrete user of the same pattern. Core should not own their dynamic labels and conditions in `_code_action.lua`. Start with feature-local registration behind an explicit enabled hook (or a small allowlist), no filesystem autoload/manifest framework. `plugin/` remains Neovim's runtime entrypoint, not the home for all optional features. Sync's `backends/obsidian.lua` is a backend adapter and belongs with sync, not automatically with every feature that mirrors the Obsidian app.

## 6. Other opportunities, after the first slices

| Cluster | High-leverage seam; what to leave alone |
| --- | --- |
| `note.lua` (1,811 lines), note creation/deletion/rename | Keep the useful `Note` interface. Extract source projection/loading, creation policy/lifecycle, and writes where they have different inputs and tests; keep relative-path selection and prompting out of the plain record. Avoid turning every method into its own file. `Note` should not need picker or LSP output to represent useful data. |
| Rename and edits | `util/rename.lua` already combines reference collection, edit assembly, LSP conversion and applying. Deepen around an edit plan keyed by file with internal `Range` and replacement text; plan first, then convert/apply at an adapter. Use existing `apply = false` paths to characterize non-mutating plan results and preserve public `WorkspaceEdit` return shapes until versioned. Don't change all note/attachment/delete operations at once: on-disk persistence, loaded buffers, stale-text checks, and undo differ. |
| Search, cache, file events | Keep ripgrep and the Lua walker as real provider implementations. Put cache and live-file result parity at the query seam where behavior is meant to agree; keep loaded-buffer precedence explicit. `cache/api.lua` runs a picker and dispatches actions; move presentation out of storage. Persisted rows (`cache`) and process-local derived values (`cache.volatile`) have different lifecycles and should stay distinct. Both consume `lsp.watchfiles`; let LSP provision/translate file events, and route normalized events through a source-neutral internal interface where cache/indexes subscribe. Keep the existing LSP watcher tests. |
| Picker | Retain `select`/preview/backend adapters. There are real alternatives (Telescope, Snacks, fzf, Mini, native); don't flatten them into one pretend implementation. Feature queries and picker entries do not need to be quickfix items (`picker.Entry` is currently an alias); convert near providers/opening. Centralize duplicated range/preview conversions, not every feature-specific formatting function. |
| Completion/inlay hints | `completion/sources/refs.lua` (~923 lines) mixes query, loaded/indexed data precedence, cancellation/staleness, rendering, and LSP `CompletionItem` construction. First extract candidate selection from rendering for a single case (block/heading), preserving current completion observability and stale checks. Distinguish hint generation/cache from the editor client that chooses and applies a hint, even if both live under `lsp/`. Do not merge their registries with public scripting. |
| Config and editing UI | Keep `config/{default,validate,removed}` distinct for now; defaulting, validation, and migration are different decisions. Document merge rules (lists, `vim.NIL`, workspace overrides) before adding more knobs or a schema generator. `ui.lua` is mostly Markdown decoration/extmarks; a narrower name such as `decorations` and a source-query interface buy more than a hierarchy of UI helpers. |

## 7. Conventions to document and enforce on new work

1. **One owner and canonical import per module.** Use `foo.lua` for a standalone module; use `foo/init.lua` for a real package with private siblings. Don't maintain both a sibling file and directory as the normal long-term form. Use a forwarding file only for compatibility, with a planned removal or a documented stable alias. Never ship both `foo.lua` and `foo/init.lua` for the same require key. `daily/init.lua` and `footer/init.lua` have no siblings; `note.lua`, `attachment.lua`, `uri.lua`, `util.lua`, and `lsp/handlers.lua` are among the file-plus-directory cases. Convert opportunistically, update explicit file paths in doc tooling, and avoid churn for modules without an ownership change.
2. **Name by domain and operation.** `link.target`, `markdown.references`, `markdown.buffer`, `editor.selection`, `lsp.commands` are more descriptive than `api`, `util`, `operations`, `sources`, or `_definition` with multiple meanings inside. Plural when the module represents a collection/concept (`references`, `commands`), singular for a value/role (`document`, `workspace`, `buffer`); avoid forcing renames solely to satisfy grammar. For LSP, use method-named files as adapters; extract shared policy into its owner instead of an underscore pseudo-layer. Use `local` for private behavior; `_` on an exported field is not privacy.
3. **Predictable file shape.** Module purpose/invariants if non-obvious, imports, module interface types/table near the top, implementation, return. Follow existing type namespace rules and put private types with their implementation. Prefer explicit named exports; moving a function to a new file is not permission to make it public. Use explicit `setup`/`attach`/`register` for module side effects. Don't use delayed `require` to justify an ownership cycle; use it for optional features/known cold paths and allow dependency direction to remain visible.
4. **Prefer small values across seams.** Source lines/snapshots, strings for paths, `Pos`/`Range`, and records with names are easier to combine than `Note | path | buffer | nil`, positional option overloads, or protocol-shaped tables everywhere. Let the convenience facade supply defaults. Specify cancellation, error, and callback guarantees when an operation spans asynchronous work; capture origin before prompting. Preserve intentional distinctions when consolidating lookalike functions.
5. **Lazy facade, explicit stability.** First remove internal imports through the root and inventory documented surfaces (`Scripting`, `Actions`, `Keymaps`, `Extensions`, `LSP`, `Note`, generated help). A fixed lazy map with memoized loads is preferable to arbitrary `require('obsidian.' .. key)`. During 3.x keep documented key spellings such as `Workspace` and test access (don't accidentally make both lowercase and uppercase permanent). Check load-on-access, unknown keys, existing enumeration if promised, and that import alone doesn't register or activate features. Separate the import-only measurement from setup and first buffer entry; don't optimize an unmeasured phase. **4.0:** choose the supported Lua surface after owners have settled, then add the comprehensive LuaLS/EmmyLua annotations for the lazy facade, generate docs from supported owners, and remove slated `Client`/legacy forwards with migration notes. Lazy loading does not imply publishing every submodule or waiting until 4.0 to reduce internal load dependencies.

## Implementation order and exit criteria

1. **Record contracts and land explicit LSP dispatch.** Add behavior tests around public hooks and intended IDs; no implicit export by table enumeration. Pull one interactive workflow out of `actions.lua` only after the call sites agree on a useful interface. Prefer link navigation as that worked example.
2. **Deepen syntax a query at a time.** Share reference eligibility and a snapshot first; only then move the touched files under `markdown/`. Marker ranges and adapter conversion become the precedent for later tag, heading, list and edit changes. No UI/search/cache-policy changes mixed into file moves.
3. **Run the path branch in parallel with characterization** if available; migrate a vertical slice (e.g. workspace resolution or attachment targets) to strings and compare behavior. Sequence the broad call-site migration after ownership of path/source/workspace policy is clear. Verify the Neovim floor and platforms in CI. Do not combine it with blanket namespace moves.
4. **Retire `api` dependencies in slices.** Workspace lookup/context, editor selection, and link/note composition are good separate PRs. Put file events and feature lifecycle behind explicit owners when a new consumer benefits; use slides/audio as the concrete test of optional feature registration. Keep temporary facade forwards, never new core callers of the forwards.
5. **Cut 4.0 interfaces deliberately.** Document supported entrypoints, deprecations/removals, string-path callback contracts, and annotations. Measure root require, setup, first Markdown buffer, and hot queries separately. Prefer narrow regression tests at real seams over a target number of files or a new import pipeline. After a seam is covered, remove tests that only assert its old private layout.

A useful deletion test for review: if deleting a proposed module only forces callers to replace one import with another, don't add it. If it makes multiple callers reconstruct the same exclusion rules, workspace precedence, command argument adaptation, or edit planning, the module earns its place.
